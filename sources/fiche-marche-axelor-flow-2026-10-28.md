# Fiche de marché — Axelor Open Suite, Open Platform et Studio face à FLOW

**État des preuves au 28 octobre 2026.** Cette fiche examine le code public Axelor comme **référence de taille et de mécanismes** pour le Core System opérationnel FLOW. Le périmètre cible est achats, ventes, stock, planification/exécution, SAV, dossier et analyse ; la finance et l'étude/développement produit sont hors du périmètre fonctionnel étudié. Les identifiants BC viennent de la [grille native FLOW](../source/grille-complexite.yaml) et des [références de marché](../source/references-couts-integration.yaml). Une dépendance logicielle à un module Finance ne transforme pas sa fonction en besoin FLOW. Une absence de preuve ne démontre pas une absence du produit.

## Références de déploiement dans des organisations de grande taille

La taille du groupe parent **ne décrit pas la taille de l'entité équipée**. Les deux cas attestent des usages Axelor ciblés ; ni leur édition ni leur version ne sont établies, et ils ne valident pas directement l'assiette de code OSS 2026 mesurée ci-dessous. Les références détaillées figurent dans le [modèle de marché](../source/references-couts-integration.yaml).

## Technologies et extensibilité

La plateforme fournit le [socle Java](https://github.com/axelor/axelor-open-platform/blob/v8.2.5/axelor-core/build.gradle) : modèles/domaines et persistance Hibernate, injection Guice, API REST, scripts Groovy, sécurité, tâches planifiées, migrations et BIRT ; le [module Web](https://github.com/axelor/axelor-open-platform/blob/v8.2.5/axelor-web/build.gradle) assemble le client. Le [client `axelor-front`](https://github.com/axelor/axelor-open-platform/blob/v8.2.5/axelor-front/package.json) utilise React/TypeScript et Vite. Le modèle métier AOS combine services Java, XML de domaines, vues, actions, tableaux/graphes, SQL/JPQL dans les vues, CSV d'initialisation et rapports BIRT. Ainsi, la réécriture d'un même mécanisme peut concerner plusieurs couches. Les XML de domaines contiennent parfois des fragments Java CDATA, par exemple [calculs GTI/GTR d'une demande client](https://github.com/axelor/axelor-open-suite/blob/e7cbea53bae88d2540f59a70b09bf0f326f1022e/axelor-intervention/src/main/resources/domains/CustomerRequest.xml) ; les métriques de lignes Java seules sous-estiment ces règles déclarées.

La composition métier a des **dépendances transverses**. Les neuf modules candidats FLOW sont `axelor-base`, `axelor-purchase`, `axelor-sale`, `axelor-stock`, `axelor-supplychain`, `axelor-production`, `axelor-quality`, `axelor-intervention`, `axelor-helpdesk`. Les [`build.gradle` des modules](https://github.com/axelor/axelor-open-suite/tree/v9.1.10) imposent en plus `axelor-crm`, `axelor-account`, `axelor-contract`, `axelor-human-resource`, `axelor-project` et `axelor-bank-payment` pour fermer leurs dépendances internes : notamment `supplychain → account`, `intervention → contract + human-resource`, `human-resource → bank-payment → account`. `axelor-account` et `axelor-bank-payment` sont **requis techniquement par cette composition AOS**, mais restent hors sélection fonctionnelle FLOW. Une architecture neuve pourrait découpler autrement ces fonctions ; le comptage source constate seulement le couplage de référence. Le [module `axelor-maintenance`](https://docs.axelor.com/aos/en/aom/maintenance/) concerne l'entretien des **machines de production** et est mesuré à part : [BC-006](../source/grille-complexite.yaml) exclut explicitement les immobilisations et l'entretien des équipements. `axelor-intervention` et `axelor-helpdesk` restent les références SAV client ; leur présence n'étend pas FLOW à la maintenance des actifs.

## Code observable et protocole de mesure

Les six dépôts publics ci-dessus ont été consultés sur les **commits exacts** indiqués. Pour une comparaison avec les autres candidats OSS, compter des **lignes physiques non vides hors commentaires** (PNCLOC) dans les fichiers source suivis par Git, en distinguant au minimum : Java et front TypeScript/JavaScript/JSX/TSX ; XML de domaines, vues et actions ; rapports BIRT ; données CSV ; tests ; code de génération et outils de build ; bibliothèques tierces. Les lignes SQL/JPQL et Java intégrées aux XML restent dans la colonne XML tant qu'un extracteur fiable ne les isole pas. Écarter `node_modules`, distributions, bibliothèques copiées/minifiées et code généré. Une mesure issue du seul working tree Windows doit vérifier les fichiers Git non matérialisés ou en collision de casse (Studio `react/mapper/src/components/form/Select.module.css` et `select.module.css`).

## Essais de parité et conséquence pour le chiffrage

1. **BC-018/046/047/048 — promesse :** soumettre deux commandes concurrentes au même stock, puis une réception future partielle et une fabrication dont la capacité est occupée. Relever quantité/date promises avant validation, réservation effective, justification du sourcing et absence de surpromesse. Distinguer disponibilité affichée, MRP, demande de préparation et engagement client.
2. **BC-025/026/053/056/059/069/073 et BC-076 à BC-085 — dossier :** relier achat, réception partielle ou rejetée, vente, livraison, réclamation, retour du bien sérialisé, intervention/réparation fournisseur et remplacement. Injecter doublon, message tardif et panne après action externe ; observer identité du bien, corrélation, effet unique, SLA et relecture historique « connu à date ».
3. **BC-086/087/088 — analyse :** afficher taux de service, retards, reliquats et retours par marque/site/période, avec sources et droits. Corriger un mouvement antidaté, puis produire les variantes et temps de passage du même dossier. Évaluer séparément tableaux AOS OSS, dashboard BPM Studio et BI Enterprise.

Pour chaque essai, consigner **version/édition, module réellement installé, configuration, extension, interface, résultat et propriétaire de financement**. Les points ouverts Buy ne créent pas de budget automatique. L'étalon Axelor sert à repérer les mécanismes à reconstruire et les dépendances à financer une fois ; une évolution du chiffrage FLOW ne serait justifiée que par un résiduel par BC et des scénarios passés/échoués, réconcilié avec les cinq options et les horizons 3/5/7/10 ans. Cette fiche est un diagnostic de marché et n'altère pas la release économique.
